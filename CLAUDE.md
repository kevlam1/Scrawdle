## What this is
- Artifact 4 of TCSS 490: a team of four building something for people outside the team. Due **Sunday, November 8, 2026 at 11:59 PM** on Canvas. Portfolio status check at end of Week 4 (Sunday, November 1).
- Idea, from the team's own pitch (`../Unit 4/Artifact 4_ Scrawdle.pdf`): a daily drawing game like Wordle or NYT's minigames.
  - Browser-based. New prompts appear once a day at a fixed time, 5-10 prompts per day, drawn from categories (exact prompt format still undecided — see Open questions in the source PDF: either a few related choices per round, e.g. [Cat ears][Bear ears][Human ears], or one fixed prompt per round).
  - Tools: pen, pencil, brush, eraser, paint bucket, lines.
  - A player can export their finished drawing (the export includes that day's prompts and the date).
  - After finishing, a player can see what other players drew for that day's prompts.
  - Drawings are stored only for the current day, then sanitized (wiped) — keeps the database small and keeps the game "daily."
  - UI reference is doodle-heavy, closer to skribbl.io's drawing screen than a polished app.
- Who it's for: the team's own framing is artists first, and the general public as a casual daily pastime — broader than the assignment's example shapes (a club, a relative's business, an open-source PR). That's a deliberate scope call by the team, not mine to second-guess, but it means "hand it over" at the end will mean putting it in front of real outside users/testers rather than one named person — worth the team confirming that's the plan.

## Stack
**Database: Supabase — now a team decision, not just Kevin's.** The updated plan doc (`../Unit 4/Artifact 4_ Scrawdle.pdf`, read 2026-11-04) crosses out Firebase under "Database considerations," so this is settled.
- No framework mandated by the idea doc. Built: plain HTML5 Canvas with vanilla JS, no UI framework — matches the doodle-heavy, low-chrome UI the idea doc asked for.
- Database: **Supabase**, over Firebase, for a specific reason tied to the daily-wipe requirement, not just a general preference (checked 2026-10-29, third-party sources only — confirm against Supabase's and Firebase's own docs before relying on this further):
  - Scrawdle needs a scheduled job that wipes the day's drawings. Supabase's free tier ships Postgres's `pg_cron` extension, so that's a plain scheduled SQL job, no billing account required ([rapidevelopers.com](https://www.rapidevelopers.com/md/supabase-tutorial/how-to-schedule-cron-jobs-with-supabase)).
  - Firebase's equivalent (a scheduled Cloud Function) needs the **Blaze** (pay-as-you-go) plan just to deploy — the free Spark plan can't deploy a scheduled function at all, even if usage would stay inside the free quota ([crontap.com](https://crontap.com/blog/firebase-scheduled-functions-without-blaze), [cronic.pages.dev](https://cronic.pages.dev/blog/scheduling-firebase-functions-without-cloud-scheduler/)).
  - Caveat: free Supabase projects pause after about a week of inactivity, so it needs a periodic ping or steady use during the term ([runhooks.app](https://runhooks.app/blog/preventing-supabase-free-tier-pausing/)).
  - **Scope, decided 2026-11-04:** Supabase stores finished drawings for the daily gallery and the list of lobby codes (`backend/supabase/schema.sql`, a real schema now, not a draft — run against Kevin's real project on 2026-11-04; the daily wipe that deletes old drawings is deployed and scheduled, see Status). It does **not** store prompts — those stay in `frontend/prompts.json`, a plain committed file, specifically so any teammate can edit the prompt pool without needing access to Kevin's Supabase project. Lobbies add one table, `lobbies`, which only records that a code exists; who is in a lobby and every game message use Supabase Realtime and are never stored (see "Lobbies and adding a multiplayer game").
  - **Keys:** the anon/public key (used in `frontend/supabase-config.js`) is meant to be public in browser code — it is not the same kind of secret the "no secrets in the repo" rule below is about, as long as Row Level Security is configured (it is, in `schema.sql`). The `service_role` key bypasses RLS entirely and must never appear anywhere in this repo. See `backend/README.md`.
  - **Known gap:** there's no login system, so anyone who has the anon key (trivially easy, since it's meant to be public) could insert a row directly, bypassing the game. `schema.sql`'s policies restrict *what* can be inserted, not *who*. There's no report/hide button in the app yet, so moderation means a teammate manually edits the database by hand.
- Hosting: Vercel (already specified in the idea doc). Live at **https://scrawdle.vercel.app**. **Once a card links to this URL, never move or rename it** (same rule as the other artifacts). Checked 2026-10-31: the deployed page 404'd at `/` because the repo has no top-level `index.html` and the real page is under `frontend/`; added `vercel.json` (`"outputDirectory": "frontend"`) to fix it. **Confirmed 2026-11-04 with `curl`:** `/` returns 200, so that fix works, and the deployed `lobby.js` matches the repo's (same hash), so a push to `main` does deploy. (At that moment `/logs` returned 404 because `frontend/logs/` hadn't been pushed yet.) The Vercel dashboard's own settings can't be seen from a session, so a "Root Directory" setting there is still unchecked, but nothing is broken because of it.
- Local caching: browser storage (IndexedDB), built in `frontend/drawing.js` — today's drawing and a Free play drawing save separately and survive a refresh.

## Lobbies and adding a multiplayer game
Kevin owns this. Read this section before you build anything that has more than one player.

- **What exists:** a **Lobby** card on the home screen (Create Lobby; friends join with the invite link, and since 2026-11-05 nobody sees or types the code itself, see `log.md` entry 54), invite links like `scrawdle.vercel.app/?BCDFG`, and a lobby room showing the invite link, who's in it (the longest-present player is the host), and a Games list. Code: `frontend/lobby.js` and `lobby.css`. The registry of valid codes is in `backend/supabase/schema.sql`. **One game so far: Scrawdle Party** (Trenten, 2026-11-05: `frontend/party.js`, `party-rules.js`, `party.css`; `log.md` entry 37). It's a working example of the contract: the host's page runs the game and every page draws its screens from messages. It reuses Zainab's drawing board through `createBoard({ ..., idPrefix })` without ever giving it a round, so it never saves over a player's drafts.
- **Adding a game:** call `ScrawdleLobby.registerGame({ id, title, minPlayers, start(ctx) })` from your own script. The full contract (what `ctx` gives you) is the comment at the top of `frontend/lobby.js`; read it first. Load your `<script>` **after** `lobby.js` in `index.html`. The host presses Start and your `start(ctx)` runs on every player's page, drawing into `ctx.container`. Use `ctx.send(event, data)` and `ctx.on(event, fn)` to sync players, and `ctx.end()` to finish.
- **Don't change the lobby for your game's sake.** If you need something it doesn't do (more players, spectators, a different host rule), ask Kevin or leave a note for him in `log.md`; don't edit `lobby.js`, `lobby.css`, or the lobby SQL yourself.
- **Realtime, not tables.** Who is in a lobby, and every message a game sends, goes over Supabase Realtime and is never stored. Don't create tables for game state. Supabase's free-plan Realtime limits (docs read 2026-11-04): **100 messages per second for the whole project**, 256 KB per message, 200 connections at once (one per player), and presence updates throttled to a handful per 30 seconds. So don't send every pointer movement: batch strokes and send a few times a second at most.
- **If a game really needs the database** (a table, a new storage folder): you can't run SQL, because the project lives on Kevin's machine. Write the change as a new numbered file in `backend/supabase/updates/` (next after `001-...`), test it if you can, and ask Kevin to run it. Drawings saved in the `drawings` bucket under `<day>/<mode>/` are removed by the daily wipe for any `<mode>` automatically.
- **Players have no accounts.** A name is chosen in the lobby; an id is made per browser tab. Don't rely on either for anything that must be trusted: anyone can send a message claiming to be someone else.
- **Kicking (Trenten, 2026-11-07, `log.md` entry 65; Kevin OK'd editing `lobby.js` for it):** the host has a **Kick** button next to each player in the lobby room, and a **Players** button in the bottom-left of a game's screen to kick during a game. Anyone else can start a **Vote to kick** from the lobby room (3+ players, one vote at a time, 30 seconds): it passes only if every player except the one being voted on says yes; one No or the time running out fails it, and that player can't be voted on again for 60 seconds. The host can be voted out too; the next player in line carries out the kick and becomes host. A kicked browser remembers the lobby and won't rejoin it that day (`localStorage` `scrawdle-lobby-kicks`). Messages are `lobby:kick`, `lobby:votekick`, `lobby:ballot`; the rules are pure functions in `lobby.js` (`mayKick`, `voteBlocker`, `voteOutcome`, `voteEnforcer`, `wasKicked`, `rememberKick`), tested in `tests/lobby.test.js`. **Same trust limits as the rest of the lobby:** a kick is only accepted from the current host or after a vote this page saw pass, but messages say who sent them and nothing checks that, and a kicked player can come back from another browser or after clearing site data. It keeps out ordinary players, not someone set on getting in. A game should treat a kicked player like one who left.
- **Limits and privacy:** up to 8 players per lobby (checked in the page, not by the server); the 5-letter code is the only thing keeping a lobby private; anyone can create lobbies, and the rows are deleted after a day. Codes use 20 consonants (3.2 million of them) so they rarely spell words.
- **Testing locally:** open the page in two windows (one normal, one private) and join the same lobby. A local copy uses the real Supabase project (the keys in `frontend/supabase-config.js`), so test lobbies and test publishes land in the real one; they're deleted by the daily jobs.

- **Name every numbered entry's heading with whoever's session actually wrote it:** `## N. Title (YYYY-MM-DD) — Name`. (2) **Know which of us you are writing as.** The four of us: `kevlam1` is Kevin, `arcangieo` is Angie, `trentenmuw` is Trenten, `zainasuw` is Zainab. Check `git config user.name` and what the person in your session has told you; if it isn't clear, ask who they are before writing. Never sign an entry as someone else. (3) **The number** is one more than the highest entry already in `log.md` (look at the file; don't count from memory).
